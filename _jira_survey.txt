## Document types in PDR
  - CCD — C-CDA clinical documents (patient summaries)
  - TRN — transaction/discharge summaries
  - LAB / ORU — laboratory results (HL7 ORU feeds)
  - ADT — admit/discharge/transfer messages (separate pipeline, counted from lookup_adt_counts)

## Rules across all reports
  - Dates come from the submission date in the S3 key path, not last-modified date (which changes on S3 rewrites).
  - One inventory snapshot (5 days ago); window ends the day before it so every day is complete.
  - Backload and processed/error prefixes are excluded.
  - HEALTHeLINK is the techbd (TechByDesign) bucket.
  - Hixny CCDs are stored under <AA>DOC; the DOC suffix is stripped so CCD and TRN match the same AA.
  - Reports 2 and 3 split the AA population: Report 2 = Salesforce hospitals (Article 28). Report 3 = everything else with data.
  - Report 4 (ADT) uses a separate data source (lookup_adt_counts) because ADT messages are not in the S3 inventory.

## Core Requirement: Per-QE Data Isolation
When a user views data through a QE’s portal, they see only that QE’s data — and nothing from any other QE.
This applies to everything: clinical records, MRN arrays, lab results, encounters, and medications. A patient like Marcus Evans exists at multiple QEs, but the Hixny view shows only Hixny’s MRNs, Hixny’s encounters, and Hixny’s labs. Switch to Bronx and the data changes completely — different MRNs, different encounters, different clinical content. This is how real QE portals work: each QE only has access to data that flowed through their network.
How the prototype implements this:
  - Patient data is organized into per-QE folders (marcus_bundle/hixny/, marcus_bundle/bronx/, etc.).
  - Each QE folder contains its own CCDs, ORU lab feeds, and TRN discharge summaries — 3 of each.
  - The build pipeline points each QE’s view at only its own folder. No cross-QE data loading.
  - The MRN array in each view shows only that QE’s source MRNs (3 per QE), not all 15.
  - Clinical data (conditions, meds, labs, vitals, encounters) comes only from that QE’s documents.
  - The shared patient identity (name, DOB, gender) and the 5 shared conditions appear in every view — those are the patient’s attributes, not a QE’s data.
In production: the same principle applies. The service backing each QE’s portal must filter by QE at query time. A QE should never see another QE’s MRNs, assigning authorities, or clinical documents. The Verato MPI links the patient across QEs, but the clinical data stays partitioned.
  - Marcus multi-QE plan
  - Prototype (5 live QE views)

## QE Patient Views (Marcus Demo)
The prototype also includes 5 live QE portal views of a synthetic patient (Marcus Evans), each showing only that QE's data — different encounters, labs, and MRN arrays per QE. 5 QEs × 3 sources each = 15 CCDs + 15 ORUs + 15 TRNs. Hixny and HEALTHeLINK use distinct visual styles; Healthix and HealtheConnections use the SMART/FHIR style; Bronx RHIO uses the IMAT style.
  - Home page with all 5 QE links
  - Marcus data plan

## What needs to happen for production
  - Wire each report to a service (Lambda or similar) that runs the SQL and returns rows. The prototype uses saved results.
  - Compute the date range from the snapshot date — the prototype has it typed in by hand.
  - Decide whether ADT should come from the inventory (once ADT data lands there) or remain a separate lookup.
  - Security, authentication and hosting are out of scope for this ticket.

## Open questions
  - Let the user choose the number of days? (10 is fixed in the prototype for Reports 2/3.)
  - Who owns getting the "Not in SFDC" sources registered?
  - Add a "Not in SFDC only" filter to Report 3?
  - Should ADT be merged into Reports 2/3 once the data is in the inventory, or kept as a separate report?
  - Add a daily trend chart (the "Doc-Type Mix by QE" placeholder)?

Entry points (on every patient view)
A Missing data control opens the capture panel, pre-populated from the patient in view and the screen/section the reviewer is on.

The panel is dismissable (× / Esc / click-outside) without submitting.
Step 1 — reviewer picks the direction of the discrepancy
PDR has it — QE does not (i.e. "in PDR, not in QE")
QE has it — PDR does not (i.e. "in QE, not in PDR")
The chosen direction is recorded on the finding.
"QE has it — PDR does not"

"PDR has it — QE does not"
QE / Source / MRN pre-filled (read-only) to the current view's QE identifier; the heading names the QE.
Reviewer gets a unique Data ID for any displayed PDR item (table row or summary-card item) via a per-item copy control, and pastes it into the finding (or reuses the last copied ID); plus Notes.
Captured on every finding
direction (PDR-has-it / QE-has-it)
Patient identity: first, last, DOB, and MPIID
QE, Source, MRN (the relevant source identity)
Data ID / document reference (for PDR-has-it) or data type + item + date + result (for QE-has-it)
MRN array — the full QE|Source|MRN set that defines the person (auto-captured, read-only)
Notes, Severity, Reviewer (from session/SSO), Report date / timestamp
PHI-safe storage (not in Jira)

## Story 3: QE-submitted review panels (backlog)

### User story
As a QE, I want to securely submit a panel of patients for side-by-side review, so that my QE can run routine side-by-side comparisons on members we choose ahead of time.
  - MVP (Michael): a secure upload of a list with MPIID, QE, source, MRN, first name and last name per person.
  - Beyond MVP: at least 2 people at the QE sign off on each submission before it becomes active.
  - Goal: QEs can do routine side-by-side reviews themselves, only on members submitted in advance and reviewed by 2 people.

### Fit with the current design
Good. A submitted panel is a review cohort supplied by the QE instead of NYeC. The existing cohort-only rule, server-held identifiers and per-member authorization all still apply. It's also a candidate way to load the PROD validation cohort.

### ⚠️ Flags
  - QE users (X1) and cross-QE visibility (X2) must be decided first.
  - The Nov 9 huddle described patients "selected randomly for review". QE-chosen panels are neither random nor NYeC-chosen, so the ARB must confirm this is acceptable.

### Proposed acceptance criteria (MVP)
  - [ ] Secure upload:
    - authenticated QE submitter;
    - CSV in a fixed template;
    - encrypted in transit and at rest;
    - malware scan on upload;
    - size and row limits (for example, ≤ 500 rows; to be decided).
  - [ ] Each row is validated against the MPI:
    - MPIID exists;
    - the QE + source + MRN tuple belongs to that MPIID;
    - first and last name match the MPI record (normalized).
  - [ ] Rows that fail validation are rejected, not added, and the submitter gets a non-PHI error report (row numbers and reason codes only).
  - [ ] A QE can only submit rows for its own QE. Rows for other QEs are rejected.
  - [ ] Accepted rows become a cohort owned by the submitting QE, with an expiry date (for example, 90 days; to be decided).
  - [ ] Audit: every upload, validation result, activation, use and expiry is audited.
  - [ ] No identifiers in URLs or logs. The uploaded file is deleted once processed (only the validated cohort is kept).

### Beyond MVP: dual sign-off
  - [ ] A panel becomes active only after 2 distinct approvers at the QE sign off. The submitter can't be an approver.
  - [ ] Approvers must have a "panel approver" role, and both approvals are audited (who, when).
  - [ ] Any change to an approved panel resets the approvals.
  - [ ] NYeC can view and revoke any panel.

### Decisions to make
# | Decision | Notes
S3-1 | Validation strictness: exact name match vs normalized/fuzzy | Fuzzy matching risks accepting the wrong person; exact matching risks rejecting valid rows. Recommend normalized exact matching (case, whitespace, punctuation).
S3-2 | Maximum panel size and expiry | This limits the risk of using panels as a bulk lookup.
S3-3 | Can panels include patients with no documents from the submitting QE? | If yes, a QE could look at people it has no relationship with. Recommend requiring an existing QE + source + MRN link.
S3-4 | What the QE reviewer sees: only documents from its own sources, or the whole PDR record? | This is decision X2.
S3-5 | Where the dual sign-off happens: in our app, or offline at the QE with an attestation? | In-app is auditable but needs QE approver accounts.
S3-6 | Upload channel: in-app upload vs SFTP/secure file exchange | In-app is simpler for users. SFTP reuses existing QE channels.
S3-7 | Retention of submitted files and validation reports | Must align with the audit retention period Compliance sets.

### Blockers
  - 🔴 X1, X2 and X3 decisions, plus an ARB follow-up review (QE users, QE-supplied cohorts).
  - 🔴 MPI validation access: the app needs read access to MPI / Patient Match (MPIID → identifier tuples, names). Use the existing mpiid-search endpoint in PM.
  - 🟡 QE user onboarding model (X4).
  - 🟡 Malware scanning service for uploads (for example, GuardDuty Malware Protection for S3).

### Risks
  - Panels used for bulk lookup. Without MPI checks and size limits, uploading names becomes patient discovery by another route.
  - Wrong-patient exposure from loose name matching.
  - Dual sign-off becoming a rubber stamp. It needs to be audited and reviewed periodically.
